# 自定义年龄组与身份证年龄校验方案

状态：用户已确认开发，主体功能已实现。日期：2026-11-06。下文保留方案与改造前现状，实际入口、实现范围及部署要求见 [开发说明](custom-age-group-development.md)。

## 1. 建议方案

保留学生组、社会组，新增可由管理员自由添加的自定义组别，例如 U8、U18、U7-U10、青少年组。它们在赛事里并列存在，每组可以独立配置项目、报名码、收费和年龄条件。

组别名称只负责展示；年龄资格由明确的规则决定，不能仅靠解析名称推断。管理员也可以创建没有年龄限制的自定义组。

“U7-U10”如果作为一个组创建，表示一个组共用项目和抽签；如果主办方实际需要 U7、U8、U9、U10 四个独立组，则分别创建四条记录。名称中的连字符不自动触发拆组。

按用户最新要求，报名字段增加“身份证号”和“性别”，各自支持“不收集 / 选填 / 必填”，新建组默认选填。开启年龄限制不自动强制身份证必填；提供身份证后自动校验，不提供则允许提交并标记年龄待核验。性别缺失同样不伪造默认值。

实际赛事存在“社会组下再分年龄组”，因此参赛类别与年龄条件应分开：参赛类别可选学生、社会、青少年或自定义；实际比赛组可命名为“社会组·35-44岁”“青少年组·U8”。第一版用扁平的赛事组记录加可选类别标签承载，不要求建立多层组别树。字段模板与参赛类别独立，不因标为学生就自动强制收集学号。

## 2. 现有项目情况

根据当前代码，而非仅参考旧方案文档：

- `EntrantType` 只有 SCHOOL、SOCIAL 两种；单项唯一约束是赛事 + 身份组别 + 项目类型。
- 报名码存在赛事的两个固定字段上；当前学生、社会两组均支持凭码免登录报名。
- 报名字段规则按 SCHOOL、SOCIAL 配置，没有身份证号字段；现有报名 DTO 和 Player 模型的性别必填，改为选填需要贯通接口、数据库和项目资格判断。
- 团体赛和收费设置也以赛事 + 身份组别作唯一约束。
- 报名、搭档、导入、转组、缴费、统计及导出等多处按两组判断。

因此需一起改造组别模型与关联流程，单独增加一个 U8 下拉选项无法支持多个年龄组独立比赛。

## 3. 管理端配置

赛事创建/编辑页，把固定两组配置升级为“参赛组别”列表。默认提供学生组和社会组，可增加自定义组；赛事也可以只启用年龄组。

```text
参赛组别                                      [+ 新增组别]
学生组      无年龄限制       男单、女单、混双       [编辑]
社会组      无年龄限制       男单、男双             [编辑]
U8          8周岁及以下      男单、女单             [编辑]
U18         未满18周岁       男单、女单、混双       [编辑]
U7-U10      7至10周岁        男单、女单             [编辑]
```

上表仅演示不同边界口径，不作为 U 命名的统一解释。

新增/编辑组别包含：

| 配置 | 建议行为 |
|---|---|
| 组别名称 | 自由填写；同一赛事内不能重名 |
| 参赛类别 | 可选标签：学生 / 社会 / 青少年 / 自定义，不用于推断年龄 |
| 字段模板 | 学生 / 社会 / 通用；自定义组默认通用，不强制填学号、学院 |
| 开启年龄限制 | 默认关闭；打开后配置上下限 |
| 年龄条件 | 选择按出生日期区间或截止日周岁；两种模式互斥，支持单边限制 |
| 年龄计算截止日 | 周岁模式默认比赛首日，可指定日期，报名开放后固定 |
| 身份证号 | 不收集 / 选填 / 必填；新建组默认选填，有年龄限制也不自动改必填 |
| 性别 | 不收集 / 选填 / 必填；新建组默认选填 |
| 比赛项目 | 沿用现有男单、女单、男双、女双、混双及团体赛设置 |
| 报名与收费 | 每组独立报名码、启停、费用配置 |

保存前显示自然语言规则，例如：“截至 2026-11-06，已满 7 周岁且未满 11 周岁。”避免只展示 U7-U10 让报名者猜测。

## 4. 年龄计算口径

参考实际赛事，第一版支持两种互斥的年龄规则，不使用虚岁：

1. 出生日期区间：直接设置最早和最晚出生日期、是否包含边界；青少年赛事优先推荐这一模式，单个出生年份可展开为当年 1 月 1 日至 12 月 31 日。
2. 指定截止日周岁：设置年龄上下限、边界及截止日期；适合规程明确要求实际周岁的比赛。

组名由管理员自由填写，不自动把 U8 转为“8岁以下”或“8岁及以下”。按出生日期模式校验时，界面直接显示准入日期区间；即使另行显示参考周岁，也不把参考周岁用于替代出生日期条件。

以下是可选配置，不宣称 U 名称在所有比赛中有统一含义：

| 名称示例 | 配置示例 | 实际资格 |
|---|---|---|
| U8 | 最高 8 周岁，包含上限 | 未满 9 周岁 |
| U8 | 最高 8 周岁，不包含上限 | 未满 8 周岁 |
| U18 | 最高 18 周岁，不包含上限 | 未满 18 周岁 |
| U7-U10 | 最低 7、最高 10，均包含 | 已满 7 周岁且未满 11 周岁 |

不设置与 U 名称绑定的固定年龄预设。上表仅作为周岁模式的配置示例；管理员保存时确认系统生成的完整资格说明即可，无须为全系统统一确定一种 U8 含义。

计算规则：截止日年份减出生年份；截止日尚未过生日再减 1。只按 Asia/Shanghai 的日历日期比较，不用毫秒差除以 365。2 月 29 日出生者在非闰年暂建议按 3 月 1 日达到新周岁，作为赛事明确公示的规则，实施前一并确认。

以截止日 2026-11-06、U7-U10 按 7 至 10 周岁为例：

| 出生日期 | 截止日年龄 | 结果 |
|---|---|---|
| 2019-11-06 | 7 | 通过 |
| 2019-11-07 | 6 | 不通过，未达到最低年龄 |
| 2015-11-07 | 10 | 通过 |
| 2015-11-06 | 11 | 不通过，超过最高年龄 |

赛事按出生年份分组时，使用出生日期区间表达，不套用比赛当天周岁。例如“2026 年赛事，2018 年出生组”可设置为 2018-01-01 至 2018-12-31，不因选手是否已过生日而改变资格。

## 5. 报名者体验

维持现有“报名码确定组别”的入口习惯：

1. 扫 U8 报名码，查看赛事介绍以及完整年龄条件。
2. 选择该组项目，填写姓名等现有资料；身份证号和性别按管理员配置展示，默认选填。
3. 提供身份证后自动展示出生日期和资格结果；周岁模式另显示截止日年龄。自动解析的出生日期与年龄不可手动覆盖。
4. 已填资料合格可提交；身份证或性别选填且为空时也允许提交，对相应受限条件标记待核验；填入的资料明确不合格则提示原因并拦截。
5. 按现有赛事设置进入审核或缴费流程。

```text
组别：U7-U10
年龄要求：截至 2026-11-06，7 至 10 周岁（含）

姓名          [             ]
身份证号      [             ]（选填，填写后自动核验年龄）
性别          [请选择 ▼     ]（选填）
出生日期      2018-08-20（自动识别）
参赛年龄      8 周岁
校验结果      ✓ 符合本组年龄要求

联系方式      [             ]（可填写监护人联系方式）
```

不合格提示示例：“截至 2026-11-06，您的参赛年龄为 11 周岁；本组要求 7 至 10 周岁，请核对身份证号或联系组委会。”系统不擅自转到其他组。

第一版沿用一名选手在同一赛事只报一个组别的规则；组内兼项仍遵循赛事原有项目数量限制。年龄区间重叠时管理员保存配置会收到提醒，但允许重叠，不按年龄自动唯一分组。

## 6. 身份证与资格校验

第一版支持中国大陆 18 位居民身份证号码，校验长度、字符格式、出生日期合法性、未来出生日期和校验位，末尾小写 x 统一转为 X。具体实现需按正式编码规则核对，不因行政区划代码变化误拒合法历史号码。

该功能验证的是“号码格式及号码中出生日期对应的年龄资格”，不等于姓名与身份证的联网实名认证。

- 没有年龄限制的组：不收集则不展示也不保存；选填则为空可提交、填了就校验格式；必填则必须提供合法号码。
- 有年龄限制的组：身份证仍遵循不收集 / 选填 / 必填设置。选填或不收集且没有证件时可提交，年龄结果为待核验；填了证件则必须格式及年龄条件均通过。
- 前端即时提示；后端从身份证重新计算出生日期、年龄、资格，不接受客户端自报年龄或“已通过”状态作为依据。
- 性别字段与项目规则分开：男单/男双要求男性，女单/女双要求女性，混双要求一男一女；性别选填且为空可提交，相关项目资格待核验。不能根据所选男单自动把本人性别存为男，也不因填写身份证而静默覆盖性别选项。
- 若需要男女同场的公开单打/公开双打，应明确增加独立项目类型并适配抽签、统计、导出，不能把现有男单/男双改名后当作不限性别项目；这是可选扩展，不作为本次默认实施范围。
- 双打双方各自按配置收集身份证和性别，分别记录核验结果，明确指出哪一方不合格或待核验。
- 团体赛每位队员按所属组条件校验，建队、导入队员和替换队员均检查。
- Excel 导入、后台手工新增、选手库选人、追加项目、后台修改及转组使用同一校验服务。历史选手缺资料时遵循目标组字段设置，选填缺失不能按必填报错。
- 管理员转组时重新检查年龄、目标项目、重复报名、兼项限制、缴费差额及现有抽签状态；校验失败时不产生部分变更。

资格状态独立于“提交成功”和缴费状态，至少区分：不适用、自动校验通过、待核验、人工核验通过、不通过。年龄或性别资格待核验时，允许收下报名，但在审核通过、进入正式参赛名单和抽签前由管理员补充核验；即使赛事设置免审核，也不能将资料不足自动视为资格通过。人工核验可线下查验，只记录结论、依据说明、核验人和时间，不强迫报名者补填原本选填的身份证号。已有资格依据被修改或删除时重新计算状态，不保留失效的通过结论。

## 7. 身份信息存储与展示

身份证只用于报名资格核验，不出现在公开名单、赛程、成绩、大屏、公开查询或普通导出中。

- 证件原文加密保存，服务端保存出生日期；用于查重的标识使用服务端密钥生成的 HMAC，不用普通哈希代替加密。
- 后台默认展示脱敏号码，普通接口不返回完整号码，也不把完整号码写入日志、错误消息、URL 或前端持久缓存。
- 确有核验权限的管理员才可查看完整号码，记录访问审计；报名端说明收集用途，并提供适合监护人代报名的提示。
- 导出默认仅包含组别、参赛年龄及校验结果；完整证件导出不纳入第一版。
- 报名查询凭证不额外授予查看完整证件的权限。
- 证件资料的保留期限和清理流程在上线前配置；历史比赛结果不依赖永久保存证件原文。

同一赛事内，有证件信息时本人、搭档、团体成员共用证件指纹进行身份匹配。无证件的旧报名继续沿用原有防重逻辑；不能承诺仅靠姓名和手机号完全识别同一个人。监护人一个手机号可为多名不同证件的孩子报名，不能只按手机号拦截。

## 8. 数据与接口改造方向

新增赛事组别实体 `TournamentGroup`，学生组、社会组也是组别记录；不把 U8、U18 等名字不断增加到固定枚举中。

建议字段：`id`、`tournamentId`、`name`、`categoryLabel`、`fieldTemplate`、`enabled`、`sortOrder`、`registrationCode`、`registrationCodeEnabled`、`fieldRules`、`ageRule`、`ruleVersion`。

`ageRule` 保存模式、是否启用，以及该模式对应的出生日期区间或年龄上下限、边界、截止日期；不是一段需要解析的自然语言。`fieldRules` 增加 identityNumber、gender 两个独立配置项。

性别未知使用 null，不增加虚假的男/女默认值；报名、搭档、Player、团体队员的 DTO、数据库字段、查询序列化和项目资格服务都需支持。报名保存年龄及性别的独立核验状态和人工核验记录，出生日期/年龄快照允许为空。仅保存相关信息不足以视为已联网实名认证。

主要关联调整：

| 对象 | 调整方向 |
|---|---|
| Event | 关联 groupId；唯一约束改为赛事 + groupId + type |
| CompetitionRegistration / Registration | 关联组别和参赛者证件资料；保存核验规则版本、截止日与年龄结果快照 |
| 搭档、团体队员 | 关联各自证件资料，不把搭档共用本人的年龄结果 |
| TeamCompetition | 按赛事 + groupId 唯一 |
| TournamentPaymentSetting | 按赛事 + groupId 唯一 |
| PaymentLog 等历史记录 | 保存 groupId 和当时组名，旧账单、旧日志继续可查 |

建议使用赛事内参赛者身份资料实体统一承载本人和搭档证件，避免把证件原文到处复制到公开选手模型。

旧 `entrantType` 仅作兼容信息，逐步停止用它决定分组；所有自定义组不能简单映射为 SOCIAL，否则仍会发生同项目冲突、收费串组和跨组误判。

报名码查询接口返回 groupId、groupName、字段规则、年龄规则及本组项目；提交时由后端确认码、组、赛事、项目关系一致。不能只信前端传来的 groupId。

登录报名目前存在赛事 + userId 唯一约束。若需要一个监护人登录账号为多名孩子报名，应改为按参赛者识别报名，账号仅作为提交人；本人既有追加报名不能仅凭账号误合并到另一个孩子。游客入口同样按参赛者而非联系电话识别。

## 9. 旧赛事兼容与规则变更

- 为已有赛事建立对应学生/社会组记录，回填现有项目、报名、团体赛、收费和日志的 groupId。
- 保留现有报名码、启停状态、表单规则、费用、eventId、比赛与抽签数据；旧二维码继续解析到对应组。
- 回填完成并核对关联、数量和收费后，再切换新唯一约束与查询。迁移应可重复执行且有备份与回滚方案。
- 旧报名不强制补身份证，旧赛事的年龄校验默认关闭。
- 新建组身份证和性别默认选填；已有组保留原性别必填规则及已有性别数据，管理员可主动改为选填，避免迁移静默改变旧赛事规则。
- 已有报名后，禁止直接修改年龄区间、截止日或开启强制年龄校验；建议新建组。若后续需要批量重校验，应单独设计影响预览和通知流程。
- 已报名组不能直接删除，只能停用入口；改名保持 groupId，不改变收费、参赛关系或历史规则快照。
- 改比赛日期不自动改变已固定的年龄截止日，避免已通过报名突然失效。
- 旧 Excel 模板继续只映射原学生/社会组；新模板按组包含“组别、身份证号、性别”等列。选填字段可为空或缺列；不收集字段忽略且不入库；必填缺列报错。身份证列按文本读取，拒绝已经损坏的科学计数法数据。

## 10. 开发范围与验收

按以下顺序实施，但完整闭环验收后再开放新年龄组：

1. 组别实体、历史回填、报名码、项目/收费/团体赛关联及接口兼容。
2. 后台组别编辑、身份证和性别字段配置、两种年龄规则与统一服务端校验。
3. 单打、双打、团体、监护人代报名及管理员录入/修改/转组。
4. 导入导出、统计筛选、缴费、公开展示、大屏及历史兼容检查。

验收重点：

- 学生、社会及至少三个自定义年龄组可在同一赛事独立存在，同类型项目不冲突。
- 生日当天、生日差一天、上下限边界、闰日和跨年按公示规则判定。
- 出生年份组不按实际生日错误拒绝；两种年龄模式分别验证边界。
- 身份证及性别选填且为空可以提交；必填缺失才拦截；不收集时客户端强行传入也不保存。缺失受限资料记录待核验，不能自动进入正式参赛名单。
- 性别未知不默认男或女；男女单/双及混双核验正确，人工核验有记录，新增身份证或修改资格资料后重新判定。
- 修改前端年龄、跳过前端校验、跨组提交、非法报名码无法绕过服务端检查。
- 双打任一方不合格、团体任一队员不合格不能通过；所有后台和导入入口行为一致。
- 同一号码重复提交和并发提交不会重复参赛；同监护人电话的不同孩子可以正常报名。
- 加密证件不进入公开响应、日志或普通导出；修改时支持保留已有证件，不接受脱敏字符串作为新证件。
- 旧二维码、旧报名、原收费与支付记录、原赛程和历史导出仍正常。
